# Coverage, fuzzing and executable examples

Use tests to distinguish correct behavior from plausible faulty implementations.

## Coverage

Write coverage profiles to the repository's artifact destination where configured, and include required integration tags when those tests are part of the measurement.

Default coverage is per package. Use `-coverpkg` deliberately when tests in one package exercise another. Use `-covermode=atomic` with race instrumentation or when accurate concurrent execution counts matter. Coverage tracks instrumented statements/blocks, not all logical branches, combinations of conditions, or assertion strength.

For each meaningful gap, identify the contract and an input that reaches it. Test both the returned outcome and relevant effects. Do not manufacture tests that merely call code to meet a percentage. Explain what remains untested when real dependencies are unavailable.

## Fuzzing

Choose a property justified by the API contract: round-trip behavior, idempotence, agreement with an independent oracle, or preservation of an invariant. State the property’s domain. For example, arbitrary byte strings are not all valid UTF-8, and a Unicode transformation need not preserve malformed encodings.

Check that the assertions reject plausible faulty implementations, including constant-empty output. Add an independent expected result or a preservation property over a constrained input domain when the contract promises preservation. Merely seeding nonempty inputs does not help if the assertions still accept losing all their content.

Every input reaching a domain-specific assertion must satisfy that domain. Prefer guarding the original fuzz input when sufficient; validate any generator against multibyte and invalid UTF-8 source inputs. For byte-oriented domains, iterate bytes: ranging over a Go string visits rune-start offsets and can leave gaps in a generated byte slice.

Seed `FuzzXxx` with representative valid, invalid, empty and boundary inputs. Keep targets deterministic and independent across inputs; bound resource use without excluding important contract cases. Nontrivial fuzz assertions may use testify with the callback's `t`.

A sanitization property such as idempotence or removal of angle brackets does not prove XSS safety. Test the actual output-context contract with an appropriate oracle and retain adversarial regression cases.

Run active fuzzing against one package and one matching target, for example `go test -run='^$' -fuzz='^FuzzDecode$' -fuzztime=30s .` from the target package. Ordinary `go test` runs seed cases and saved corpus inputs without performing a fuzzing campaign. Preserve minimized failures as regression inputs and report the scope of the run without claiming proof.

## Examples and golden files

Executable `Example` functions teach the public API while checking output. Use an external test package, associate names with exported symbols, and begin a named example suffix with a lowercase letter. An `Output:` directive runs and checks the example; without it the example is compiled but not executed. Use `Unordered output:` only when order is outside the contract.

Golden files suit large structured outputs when a reviewer can assess meaningful differences. Normalize only nondeterminism outside the contract. Updating snapshots is an explicit operation whose diff needs review; a failing test must not silently overwrite its expected output.
